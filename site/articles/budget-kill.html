Comment j'ai empêché un agent IA de brûler 850 $ pendant la nuit

Une nuit de mars, un agent autonome que je testais a failli cramer 850 $ en crédits Claude sur une tâche simple. Voici exactement ce qui s'est passé, pourquoi mon code l'a arrêté à 12,40 $, et comment vous pouvez reproduire le même garde-fou en moins de 80 lignes.

Chady Emara · 12 min de lecture · Code inclus · reproductible

1. Le setup — un agent qui devrait être sage

Je travaillais sur une tâche banale : un agent chargé de scanner un gros repo de docs (environ 4 000 fichiers markdown), d'extraire pour chacun une fiche structurée {title, summary, topics, last_reviewed}, et de remplir une table Postgres. Le kind de tâche qu'on confie volontiers à un agent parce que c'est long, répétitif, et que ça ne demande pas beaucoup de jugement.

Paramétrage de base : Claude Haiku 4.5, tools read_file, list_dir, insert_row. J'avais donné à l'agent une consigne simple : "traite les 4 000 fichiers, insère une ligne par fichier, ping-moi quand c'est fini." J'ai lancé ça à 23h30 avant d'aller me coucher. La veille, j'avais fait tourner la même config sur 200 fichiers. Ça avait marché. Coût : 0,78 $. Extrapolation naïve pour 4 000 : 15 $, 16 $. Confortable.

Spoiler : l'extrapolation linéaire est fausse. Les agents ne se comportent pas linéairement quand on multiplie par 20 la taille de l'input. Ils se comportent non-linéairement mal.

2. La timeline — comment on passe de 0,78 $ à presque 850 $

23:31
Lancement de l'agent. Budget soft cap : $20. Budget hard cap (kill-switch) : $50.
23:47
L'agent a traité 180 fichiers. Coût : $0,92. Tout va bien.
00:12
Un fichier tombe dans un format auquel l'agent ne s'attendait pas (vieux markdown avec front-matter YAML malformé). L'agent n'arrive pas à parser. Il retry. Et retry. Et retry.
00:14
L'agent décide de "lire plus de contexte" pour comprendre le fichier. Il charge les 10 fichiers voisins. Ça ne l'aide pas. Il ré-essaie avec 20 fichiers voisins.
00:21
Coût cumulé : $4,10. Le rythme a triplé en 7 minutes. Le kill-switch se met à surveiller sérieusement.
00:34
L'agent, toujours bloqué sur le même fichier, décide qu'il a besoin "de relire l'intégralité des règles que je t'ai données, plus l'historique de mes tentatives". Chaque turn contient maintenant ~60 k tokens d'input.
00:52
Coût cumulé : $12,40. Le hard cap est atteint. Le runtime déclenche BudgetExceededError. L'agent est stoppé.
08:14
Je réveille, je lis les logs. Sans le kill-switch, extrapolation du rythme observé entre 00:21 et 00:52 : ~850 $ consommés en 8 heures.
L'agent n'avait pas eu d'intention malveillante. Il avait juste rencontré un cas qu'il ne savait pas gérer et s'était engagé dans une spirale d'exploration coûteuse pour essayer de s'en sortir. C'est exactement comme ça que les incidents arrivent en production.

3. Pourquoi un budget mental ne suffit pas

Au début, je pensais qu'il suffisait d'écrire dans le prompt système : "ne dépasse pas 20 $ de coût". Ça ne marche pas, pour trois raisons :

  • L'agent ne voit pas le coût. Il n'a pas accès au compteur de tokens. Il ne sait pas combien il a brûlé depuis le début de la session, sauf si vous le lui dites.
  • Même s'il le voit, il ne raisonne pas bien dessus. Les LLMs sont mauvais pour le calcul progressif. Lui dire "tu as 20 $" au départ et espérer qu'il gère, c'est comme demander à un chat de faire ses comptes.
  • Une décision de limitation doit être déterministe. Le kill-switch ne peut pas être une suggestion : "si tu veux bien, arrête-toi". Il doit être câblé en dur dans le runtime, hors du contrôle du LLM.

La bonne architecture tient en une phrase : le coût est compté par le code, pas par le modèle. Et quand le code dit stop, le modèle n'a pas voix au chapitre.

4. L'architecture du kill-switch

Trois composants, reliés par un contrat simple :

  • CostTracker — un petit objet qui intercepte chaque appel au modèle, additionne les tokens (input + output) et traduit en dollars selon le pricing du modèle utilisé.
  • BudgetPolicy — la configuration : combien je m'autorise à dépenser sur cette tâche ? Soft cap (warning), hard cap (kill).
  • TurnLoop — la boucle qui fait tourner l'agent. Avant chaque tour, elle interroge le CostTracker. Si le hard cap est dépassé, elle lève une exception avant l'appel modèle. Pas après.
Le point clé

La vérification arrive avant l'appel, pas après. Un check "tu as dépassé, arrête-toi la prochaine fois" arrive toujours trop tard. Un tour supplémentaire, c'est potentiellement des milliers de tokens de plus.

5. Le code minimal — 80 lignes suffisent

Voici la version dégraissée, en TypeScript. Elle marche avec n'importe quel SDK d'agent (Claude, OpenAI, Mistral). Version complète et typée dans le repo Orchestre, mais cette version-là se suffit à elle-même pour comprendre l'idée :

cost-tracker.ts
type Pricing = { inputPer1M: number; outputPer1M: number }

type Usage = { inputTokens: number; outputTokens: number }

export class CostTracker {
  private totalCostUSD = 0
  constructor(private pricing: Pricing) {}

  record(usage: Usage): void {
    const cost =
      (usage.inputTokens / 1_000_000) * this.pricing.inputPer1M +
      (usage.outputTokens / 1_000_000) * this.pricing.outputPer1M
    this.totalCostUSD += cost
  }

  get cost(): number { return this.totalCostUSD }
}

export class BudgetExceededError extends Error {
  constructor(public readonly spent: number, public readonly cap: number) {
    super(`Budget exceeded: spent $${spent.toFixed(2)} > cap $${cap.toFixed(2)}`)
    this.name = 'BudgetExceededError'
  }
}

export type BudgetPolicy = { softCapUSD: number; hardCapUSD: number }

export function enforceBudget(tracker: CostTracker, policy: BudgetPolicy): void {
  if (tracker.cost >= policy.hardCapUSD) {
    throw new BudgetExceededError(tracker.cost, policy.hardCapUSD)
  }
  if (tracker.cost >= policy.softCapUSD) {
    console.warn(`[budget] soft cap reached: $${tracker.cost.toFixed(2)}`)
  }
}
turn-loop.ts
import { CostTracker, BudgetPolicy, enforceBudget } from './cost-tracker'

type AgentStep = () => Promise<{ done: boolean; usage: { inputTokens: number; outputTokens: number } }>

export async function runBoundedLoop(
  step: AgentStep,
  opts: { maxTurns: number; tracker: CostTracker; policy: BudgetPolicy },
): Promise<{ turns: number; finalCost: number }> {
  const { maxTurns, tracker, policy } = opts

  for (let turn = 1; turn <= maxTurns; turn++) {
    // CHECK BEFORE CALL — jamais après
    enforceBudget(tracker, policy)

    const { done, usage } = await step()
    tracker.record(usage)

    if (done) return { turns: turn, finalCost: tracker.cost }
  }

  throw new Error(`Max turns exceeded (${maxTurns})`)
}

C'est tout. Ajoutez un logger si vous voulez, persistez les événements sur disque si vous voulez. L'idée fondamentale tient dans les 40 lignes ci-dessus : un compteur, une policy, et un check avant chaque appel.

6. Les erreurs classiques

6.1 Soft cap = hard cap

Mauvaise idée. Le soft cap est un warning qui vous permet d'investiguer en direct (envoyer un Slack, activer un mode verbose, spéculer sur la suite). Le hard cap est la mort. Les deux servent à des choses différentes. Typiquement j'utilise softCap = hardCap * 0.6.

6.2 Compter uniquement les tokens output

Erreur très courante. En mode agentique, l'input gonfle à chaque tour (on réinjecte l'historique). À 10 000 tokens d'output, vous pouvez avoir 200 000 tokens d'input accumulés. Ne comptez jamais que l'output, vous vous retrouverez avec des factures trois fois plus élevées que prévu.

6.3 Oublier le context window

Le hard cap budget doit être doublé d'un hard cap tokens par tour (typiquement 90% du context window du modèle). Sinon l'agent finit par se prendre une erreur "context too long", re-essaie, re-échoue, et brûle des tokens à ne rien faire.

6.4 Faire confiance au LLM pour s'auto-limiter

Déjà dit, je le répète parce que c'est la plus grosse erreur que je vois chez les gens qui débutent : ne faites jamais confiance au LLM pour ses propres limites. Les limites sont du code. Pas du prompt.

Je n'ai jamais rencontré, sur aucun projet, une raison valable de ne pas avoir de kill-switch. C'est littéralement l'optimisation la plus rentable que vous puissiez faire sur un agent, et elle prend une demi-heure.

8. Aller plus loin

Ce qu'on vient de voir est le minimum absolu. Une version production-grade (qui est ce qu'Orchestre implémente) ajoute :

  • Budget hiérarchisé — un budget global, un budget par wave, un budget par feature, un budget par tool-call. Les enveloppes s'emboîtent comme des poupées russes.
  • Event store — chaque tour écrit un événement signé dans un fichier .jsonl. Vous pouvez replay, auditer, prouver.
  • Memory d'échecs — le pattern qui a fait exploser le budget est stocké et réinjecté la prochaine fois pour éviter la récidive.
  • Graceful degradation — quand le soft cap est franchi, l'agent passe en mode "simplifie, n'explore pas, boucle moins" avant d'être tué net au hard cap.
  • Propagation — quand plusieurs agents coopèrent, le budget parent propage sa contrainte aux enfants.

Tout ça est dans le repo Orchestre, open-source, MIT, testé à 308 tests. Si le sujet vous intéresse, la démo examples/runtime-demo/demo.mjs montre l'ensemble du dispositif en marche sur une tâche réelle en ~30 événements observables.

9. Ce que je retiens de cette nuit

Un agent IA est un processus autonome qui consomme de l'argent réel à la vitesse à laquelle il parle. C'est une nouvelle classe d'objets dans le monde logiciel. Le réflexe "je fais confiance au prompt, j'envoie en prod" est le même réflexe qu'un dev de 1995 qui désactive les try/catch parce que "mon code ne plante jamais". Ça marche jusqu'au jour où ça ne marche plus — et ce jour-là, ça coûte très cher.

La bonne nouvelle : on sait comment faire. On l'a toujours su, en fait. Il suffit d'appliquer aux agents ce qu'on applique à n'importe quel processus long-running : un quota, un timeout, un kill-switch, un journal. La technologie est là. Il manque juste que ça devienne un réflexe — comme taper ulimit avant de lancer un job suspect.

Si vous déployez des agents et que vous n'avez pas cette couche aujourd'hui, ce n'est pas un problème de compétence, c'est un problème d'outillage qui n'a pas encore été standardisé. C'est exactement le vide que j'essaie de combler avec Orchestre.
